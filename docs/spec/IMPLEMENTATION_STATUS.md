# Implementation status

The measurable answer to "is the specification implemented?" — a set of requirement
identifiers, each with the evidence that closes it. Maintained by AUTHOR runs inside
the pull request that changes a requirement's status.

An identifier moves to `IMPLEMENTED` only when code satisfies it **and** a test
proves it. "The code looks right" is not evidence.

## Legend

| Status | Meaning |
| --- | --- |
| `IMPLEMENTED` | Merged, with a named test that fails without the change |
| `PARTIAL` | Merged code covers a named slice; the rest is explicitly open work |
| `BLOCKED` | Cannot proceed; the blocking question is in `OPEN_QUESTIONS.md` |
| `DEFERRED` | Deliberately out of scope for now, with a recorded reason |
| `CONTESTED` | Implementable only after the researcher resolves a contradiction |
| `NOT_STARTED` | Present in the registry, with no ledger row |

The `Spec` column is the specification's own status for that identifier, mirrored from
`REQUIREMENTS_REGISTRY.csv`. A `REVIEW` row is not executable yet, so `NOT_STARTED`
beside it means "not offered for implementation", not "skipped".

Only `IMPLEMENTED` is evidence: a merged pull request plus a named test that fails
without the change. Every other status is a statement about work that is not done.

## How this table is maintained

It is not maintained. It is generated by `scripts/implementation_status.py` from
`docs/spec/implementation_status.csv` — the ledger — and the mirrored requirements
registry. The `policy-guard` check regenerates it and fails on any difference, so a
hand-edited table cannot survive.

An AUTHOR run records evidence by appending **one ledger row inside the same pull
request as its work**, then regenerating:

```sh
python scripts/implementation_status.py
```

A ledger row's presence on `master` **is** its merge evidence: the row arrives exactly
when the work does. Nothing later has to flip a status, which is why there is no
reconciliation step here any more — the previous one existed only because this file
stored a status that a merge elsewhere invalidated, and it cost an AUTHOR run and an
ACCEPTOR run every time it fired.

Claimed but unmerged work is a `status:in-progress` label on its Issue. The forge owns
that fact; this file does not.
